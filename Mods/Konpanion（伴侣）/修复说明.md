## 一、上一版为什么没生效（已用日志坐实）

第三版加了两道防线，结果**两道互相抵消了**：

```
第一道（状态机修复）把 od.GameObject.UseVariable 改成 false
        ↓
第二道（解析钩子）却要求 fgo.UseVariable == true 才生效
        ↓
钩子被自己的修复绕过 —— 日志实测「已拦截」0 次
```

而且日志给出了完整的时序，证明污染发生在**场景加载之后**：

| 时刻 | CanInput 目标解析 |
|---|---|
| 第 1 次场景加载（刚进游戏） | `Knight` ✓ → 判定【应可休息】 |
| 第 3 次场景加载后（诊断 dump） | `Knight` ✓ `UseVariable=False`（修复已生效） |
| 读档后按上键进入「Can Rest?」 | **`kompanion`(-133104)** ✗ → 判定【被取消】 |

也就是说：`OnNextLevelReady`（场景加载）那一刻是好的，
**克隆体是在关卡里被重建的，把已经修好的引用又拽走了** ——
那时已经没有任何防线在岗。

## 二、第四版修正

钩子的判定条件**只保留"变量名恰为 Hero"这一条**，不再看 `UseVariable`：

```csharp
var fgo = ownerDefault.GameObject;
if (fgo == null) return result;

// 只认同一个特征：变量名恰为 "Hero"
// 不能把 UseVariable 当条件 —— 状态机修复会把它关掉，钩子就会被自己的修复绕过
if (!string.Equals(fgo.Name, "Hero", StringComparison.Ordinal)) return result;

var hero = HeroController.instance?.gameObject;
if (hero == null || result == hero) return result;
return hero;    // 解析结果不是小骑士本体 → 改回本体
```

这样无论引用是"变量引用"还是被改成"直接引用"，只要它的名字还是 `Hero`，
解析结果一旦不是小骑士本体就会被当场纠正 —— **时机无关，也不需要任何周期遍历**。

另外加了一行存活日志，用来确认钩子到底有没有被调用：

```
[伴侣] 英雄引用解析钩子已生效（Fsm.GetOwnerDefaultTarget 已挂接）
```

**这条不出现，说明钩子压根没被 PlayMaker 走到**，那就是另一条排查路径了。

## 上一版为什么仍然 0 命中

第三、四版新增的钩子**根本没被订阅** —— 补丁脚本在给源码做多行替换时，
因换行符（CRLF 与 LF）不一致而静默失败，只有单行替换生效。
所以 DLL 里写着钩子方法，却从来没有接到 PlayMaker 上。
这类失误已通过"替换必须断言 + 交付前 grep 复核"堵住。

## 第五版的新防线

```csharp
private void OnFsmStateEnter(orig, FsmState self)
{
    if (self.Fsm.Name == "Bench Control" && self.Name == "Can Rest?")
        FixHeroRefsInState(self);   // 必须在 orig(self) 之前
    orig(self);
}
```

**为什么选这个点**：

- 时机最精确 —— 玩家按下上键、动作即将执行的那一刻，引用被摆正；
- 不依赖可能被 JIT 内联的小方法（`Fsm.GetOwnerDefaultTarget` 体量很小，内联后 detour 会失效）；
- **此方案此前在独立的长椅修复模组中已经过验证有效**，只是当时做成了单独模组；
  现在它被并入本模组，不再需要额外安装任何东西。

同时保留：场景加载后/创建伙伴后的引用清理，以及解析钩子（多一层保险）。
